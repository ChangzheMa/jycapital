# 持续任务的后台监控

监控脚本是 [monitor-run.py](../scripts/monitor-run.py)，仅使用 Python 标准库。它接入已有进程，读取运行目录的 `manifest.json` 和 `events.jsonl`，定期写入 `monitor-state.json`；普通进度不输出通知。脚本不执行模型训练、参数修改、重试、平台提交或 Git 操作。

```powershell
.venv/Scripts/python.exe .agents/skills/jycapital-experiment/scripts/monitor-run.py --run-dir outputs/runs/<run_id> --pid <任务进程ID> --interval 10 --report-seconds 3600 --stall-seconds 900
```

`--stall-seconds` 根据任务阶段的正常耗时选择；省略时不按日志静默时间判断停滞。长时间没有分片日志不必然表示进程故障。脚本同一时间只允许一个监控实例使用同一运行目录；状态文件可供用户询问时即时读取。

标准输出及 `monitor-notifications.jsonl` 仅包含需检查的事件：每小时汇总、训练权重冻结／明确阶段完成、任务完成、失败／中断、进程退出或可能停滞。训练内部每轮验证预测完成仍属普通进度，不单独唤醒。每个阶段和同一异常去重；阶段结束时重置小时汇总计时。若进程退出但结果文件尚无成功状态，只报告进程已退出，不把退出码为零当作模型评测通过。

## 与宿主对话连接

- 优先使用宿主支持的后台任务完成通知或向当前任务发送消息的机制，将上述通知送回原对话。只通知已授权的当前任务，不新建模型任务或代理来轮询。
- 发送器须在主对话结束后仍能独立执行，优先由独立后台进程直接调用宿主通知接口。持续工具单元转发也须验证主回合结束后仍会及时发送，每条发送路径分别验收。
- 当前宿主若提供 `send_message_to_thread`，先核对目标任务标识再发送；例如读取 `CODEX_THREAD_ID` 并与活动任务列表核对。通知只含事件、运行标识和状态文件位置，详细日志留在本地，不发送行情、凭据或长堆栈。
- 空闲验收应先确认主对话进入空闲，再发送后台通知，核实宿主自动开始新回合，并由接收回合记录事件标识和确认时间。活动回合内收到消息、接口返回成功或本地文件产生通知均不能代替该验收；需要用户再次发消息才恢复执行的路径不算自动唤醒。
- 普通日志检查与进程等待留在脚本／工具编排层；这些检查不应生成新的 LLM 回合。不要每几十秒返回一次模型，只为了读日志、报告一个月份或再次等待。
- 宿主没有独立回调或尚未通过空闲验收时，保持后台监控的工具等待到事件发生；内部短等待不反复返回给 LLM，用户新消息应能中断等待。明确区分本地监控、消息接受和对话恢复执行，未通过验收的路径不得宣称可以在结束对话后自动跟进。
- Windows 使用 `Start-Process` 时设置 `-WindowStyle Hidden`；也可使用宿主自带的后台执行会话。监控输出、进程标识和通知状态保存在被忽略的 `outputs/` 中。

收到结束通知后，读取实际结果确认完成状态，再继续已授权的验证／测试、版本比较和条件导出。正常进度没有通知时，无需新增对话消息。
