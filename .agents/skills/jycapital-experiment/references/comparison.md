# 比较、晋级与平台成绩

在选择参照、生成比较报告、判断候选或接收平台分时阅读。仓库当前协议和本次用户约定优先于本文中的默认值。

## 三类参照

| 角色 | 选择方式 | 缺失时的处理 |
| --- | --- | --- |
| 本地验证最优 | 从可比、已完成的历史运行中按验证集主指标选优；当前是 `rank_ic_mean` 最大值 | 无历史有效实验时可建立首个基线；有历史记录但缺文件不等于没有参照 |
| 平台最优 | 在同一平台评分口径/榜单下，从有可靠分数的提交中按其排序方向选优 | 明确写“暂无平台成绩”，继续本地比较；不填 0，不用平台可运行状态替代分数 |
| 父版本 | 本次方案实际继承的版本及对应运行，优先使用用户指定的父版本 | 从零设计可为空；不要为了凑满三项编造父版本 |

启动前或从历史集合选择参照时排除当前新 run，避免把它先登记成最优后与自己比较。多个角色对应同一 run 时保留角色列表、合并数据行。没有用户指定父版本但确实在某个实现上修改时，记录实际继承关系。

本地最优和平台最优是两条独立记录，不要求是同一个模型。平台最优模型若有可比的本地结果，把它的本地验证/测试表现纳入对比；新模型尚无平台分时，官方分差记为未知，不能宣称超过平台最优。

## 可比性检查

核对协议及指标实现版本、标签来源和指纹、股票池指纹、评估日期、有效样本和缺失处理规则。模型输入频率、窗口、网络或训练方法可以不同，不因这些实验变量变化直接拒绝比较。

现有 `scripts/compare.py` 可用于基础表格和指纹检查，但尚不自动选择三类参照、计算全部差值、汇总逐月稳定性或管理平台成绩。需要时扩展仓库工具或基于已保存产物计算；不能把并排打印几行指标当作已经完成提升分析。

协议/标签/评估实现变更时，给新协议明确标识，并尽可能用历史冻结权重和对应推理实现重评同一区间；不要覆盖旧结果或仅改元数据让指纹相等。未建立可比结果时，不作可直接比较的提升结论。

预测覆盖不同应报告原始股票池分母、最低截面覆盖、缺失截面和共同样本上的配对比较。原始覆盖结果必须保留，不能只展示过滤后的共同样本好成绩。默认晋级不接受通过降低覆盖来换取更高相关系数。

缺少历史逐截面预测时，可比较已有且可验证的汇总指标，但明确无法完成哪些配对或稳定性检查。缺少关键口径证据则标记不可比，先补证据或重评，不用猜测填补。

## 比较结果

至少保存以下信息；不要固定成只有 v1 才具备的字段或写死旧分数：

- 当前 `solution_id`、`run_id`、父 run、协议、实际源码/配置/模型指纹。
- 三类参照的角色与 run/submission 标识，以及哪些参照缺失。
- 验证和测试两套结果：IC、Rank IC、相应未年化 IR、MSE/MAE、有效样本数、覆盖和未定义相关系数截面数。
- 新旧指标及有符号差值。提高为好的指标用 `new - reference`；误差等降低为好的指标注明方向，可另列 `reference - new`。旧值为零、负数或接近零时，不给误导性的相对百分比。
- 各月相同区间的配对差值、改善/退化分布，解释总均值是否被少数月份驱动。
- 参数规模、训练与推理耗时、相关资源开销及测量环境；不同机型/软件环境的耗时不直接解释为算法加速。
- 平台分及其来源/口径；未知分数与本地指标分列，不相减、不合成为自创总分。
- 是否改善、是否导出、判断依据、明显代价和证据局限。

每个版本都展示测试结果。逐 epoch 的 checkpoint 选择仍只用验证指标；不要根据测试分选 epoch/种子，再把该结果称作独立测试。长期反复观察后的测试期属于已观察的研究评估区间，应说明这一限制。

默认只跑一个种子时，只能得出该种子的观察结果。用户授权多种子复验时，新旧方案使用相同种子集合和比较条件，报告均值及波动；不能只给新方案挑最佳种子或单方面增加训练预算后声称公平比较。没有预先约定显著性或提升阈值时，不伪造统计置信度，也不暗自增加硬门槛。

## 改善候选的默认判定

1. 训练、验证、测试完成，比较口径与输出/因果性检查通过。
2. 验证主指标高于可比历史本地验证最优；当前采用 `rank_ic_mean`，不是绝对值最大的相关系数。
3. 覆盖率不降低，没有依赖缺失、泄漏、未来信息等使结果失效的问题。

三项满足时可认定为本地改善候选。测试、次要指标或耗时出现代价时，突出报告，避免“全面提升”的表述；不在看到结果后临时更改晋级标准。只有更高测试分、只有超过父版本、只有更快但主指标下降，均不满足默认判定；用户希望采用这种取舍时先明确新目标。

若此前完全没有有效历史版本，首个通过检查的运行可作为基线候选。若已有版本只是缺少本机产物，先从索引/仓库冻结材料恢复证据，不能据此跳过比较。

正式平台分在导出、推送和用户提交后才可能得到，所以导出前不要求新模型必须已有平台分。平台最优用于参照，不成为等待新分数的循环前置条件。

## 平台成绩回填

只使用用户明确提供的成绩或用户指定、实际可用的查询方法。不要自行假定能访问平台账户，不把没有查询能力解释为 0 分，也不因缺平台分停止已可进行的本地工作。

将新成绩绑定到可确定的 `submission_id`、`run_id` 和模型哈希，并保存：

- 原始指标名/值、排序方向；“第几名”和数值分数分开。
- 公榜/私榜等评估阶段、可获得的区间或评分版本，防止跨榜单直接排序。
- 平台提交 ID（若有）、结果状态、成绩获取/确认日期和时区。
- 证据来自用户告知还是指定查询；不能把用户告知改写成代理亲自验证。

成绩属于哪个版本、哪个指标或什么榜单存在歧义时先澄清，保留原始反馈，不先覆盖现有最优。重复反馈不重复增加实验次数，修订分数时保留必要来源。

当前 CSV 有单个 `platform_score` 和 `platform_submission_id`。需要多个指标、评分上下文或来源时，在相应结果 JSON 增加结构化记录，并维持 CSV 为简洁索引；不要向 CSV 单元格随意塞难以解析的多指标文本。保留既有列顺序和 UTF-8 BOM，只有有意迁移结构时才改列。

平台可运行、正式提交通过、官方评分是三种不同结论。收到“平台上可以运行”只能登记第一项。新平台分不自动触发重训、导出或推送；按当前请求范围更新记录和平台最优，必要时再讨论下一步研究方向。
